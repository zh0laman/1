# Интерактивы видеозвонка (под веб-реализацию)

Документ описывает, как сейчас работают интерактивы в звонке, чтобы сделать веб-версию с тем же поведением.

Охват:
- `Поднять руку`
- `Чат в звонке`
- `Реакции`
- `Whiteboard`

Основа текущей реализации: `LiveKit Data Channel`.

## 1. Общий принцип синхронизации

### 1.1 Транспорт
- Все интерактивы внутри активного звонка ходят через `room.localParticipant.publishData(...)`.
- Для `raise_hand`, `call_chat`, `call_reaction` используется общий Data Channel (без отдельного topic), обычно `reliable: true`.
- Для `whiteboard` используется отдельный topic: `alem.whiteboard`.

### 1.2 Роутинг входящих сообщений
- Клиент слушает `DataReceivedEvent`.
- Если `event.topic == 'alem.whiteboard'`, payload передается в whiteboard-модуль.
- Иначе маршрутизация идет по `payload.type`:
  - `raise_hand`
  - `call_chat`
  - `call_reaction`
  - часть whiteboard-событий тоже поддерживается по `type`.

### 1.3 Базовая рекомендация для веба
- Сделать единый `InCallDataBus` слой:
  - `publish(payload, {topic, reliable, destinationIdentities})`
  - `subscribe(type/topic)`
- Все интерактивы держать как отдельные модули поверх этого шины, чтобы не смешивать UI и сетевую логику.

## 2. Поднять руку

## 2.1 Что делает пользователь
- Нажимает кнопку "рука" на панели звонка.
- Повторное нажатие снимает поднятую руку.

## 2.2 Payload

```json
{
  "type": "raise_hand",
  "identity": "participant_identity",
  "sender_name": "Имя пользователя",
  "value": true
}
```

Где:
- `value=true` -> поднял руку
- `value=false` -> опустил руку

## 2.3 Как это обрабатывается
- Локально сразу обновляется состояние `_isHandRaised`.
- У всех участников обновляется карта `raisedHands[identity] = value`.
- Если руку поднял другой пользователь, показывается короткий notice (пример: `"Иван поднял руку"`).

## 2.4 Как это отображается
- На кнопке "рука" у автора включается активный стиль.
- На плитке участника появляется иконка поднятой руки.

## 2.5 Что важно учесть в веб-версии
- Состояние должно быть персессионным внутри комнаты: `Map<participantId, boolean>`.
- При выходе участника из комнаты желательно чистить его ключ из карты.
- Рекомендовано добавлять небольшую debounce-защиту от быстрых повторных кликов.
- После reconnect нужно восстановить состояние. Практичный вариант:
  - хранить `raisedHands` в памяти текущего звонка
  - при reconnect переотправлять локальное состояние руки.

## 3. Чат в звонке

## 3.1 Что поддерживается
- Общий чат (`Всем`).
- Приватное сообщение конкретному участнику (`Лично`).

## 3.2 Payload

```json
{
  "type": "call_chat",
  "id": "msg_unique_id",
  "sender_id": "participant_identity",
  "sender_name": "Имя отправителя",
  "recipient_id": "participant_identity_or_absent",
  "recipient_name": "Имя получателя_or_absent",
  "text": "Текст сообщения",
  "ts": 1770000000000
}
```

Правила:
- Если `recipient_id` отсутствует -> сообщение для всех.
- Если `recipient_id` заполнен -> это личное сообщение.

## 3.3 Правила фильтрации входящих
- Если сообщение приватное и адресовано не мне, оно не попадает в локальный список.
- Если сообщение мое (`sender_id == localIdentity`), оно всегда показывается у меня.

## 3.4 UI-поведение
- Панель чата открывается/закрывается отдельно от основного экрана звонка.
- Пока панель закрыта:
  - входящие не-мои сообщения увеличивают `unreadCount`.
- При открытии панели:
  - `unreadCount` сбрасывается в `0`.
- В bubble для приватных сообщений:
  - у отправителя: `Лично: <имя>`
  - у получателя: `Лично вам`.

## 3.5 Как это делать в вебе
- Держать отдельный store:
  - `messages[]`
  - `isPanelOpen`
  - `unreadCount`
  - `selectedRecipientId`
- Автоскролл вниз делать только если пользователь внизу списка, чтобы не ломать чтение истории.
- Валидация отправки:
  - `trim(text).length > 0`
  - ограничение по длине сообщения (например 1-2k символов).
- Для групповых звонков обязателен селектор "Кому" с `Всем + список участников`.

## 4. Реакции

## 4.1 Что поддерживается
Разрешенный набор эмодзи:
- `👍`
- `❤️`
- `😂`
- `👏`
- `🎉`
- `😮`

## 4.2 Payload

```json
{
  "type": "call_reaction",
  "id": "<timestamp>_<sender_id>_<emoji>",
  "emoji": "🎉",
  "sender_id": "participant_identity",
  "sender_name": "Имя",
  "ts": 1770000000000
}
```

## 4.3 Серверная логика не требуется
- Реакции в этой части идут peer-to-peer внутри LiveKit комнаты через data channel.
- Клиент добавляет локальный optimistic echo сразу после отправки.

## 4.4 Ограничения и защита от спама
- Отправка троттлится (`~350ms` между отправками).
- Неподдерживаемые эмодзи игнорируются.
- Дубликаты отбрасываются по `id`.

## 4.5 Отображение
- Реакции живут ограниченное время (`~4.8s`) и исчезают автоматически.
- На экране одновременно держится не более `20` активных реакций.
- Показывается эмодзи и имя отправителя (короткий плавающий overlay).

## 4.6 Рекомендации для веба
- Хранить `activeReactions[]` + таймер удаления по `id`.
- При переполнении удалять самую старую.
- Для слабых устройств предусмотреть degraded animation mode (меньше blur/теней).

## 5. Whiteboard

## 5.1 Канал и модель
- Topic: `alem.whiteboard`.
- Координаты нормализованные (`0..1`), чтобы одинаково работать на разных разрешениях.
- Модель объектная: strokes + shapes + text + sticky + background + brush config.

## 5.2 Основные события протокола
- `whiteboard_open`
- `whiteboard_snapshot_request`
- `whiteboard_snapshot`
- `draw_event` (`start|move|end|clear_all`, включая `is_eraser`)
- `whiteboard_element_add`
- `whiteboard_element_update`
- `whiteboard_element_remove`
- `whiteboard_background_change`
- `whiteboard_brush_config_change`

## 5.3 Снимок состояния (snapshot)
Используется при входе нового участника и после reconnect.

Структура:

```json
{
  "version": "2.0",
  "type": "whiteboard_snapshot",
  "sender_id": "host_identity",
  "payload": {
    "elements": ["..."],
    "background": "pattern",
    "brush_config": {
      "pen_width": 3,
      "eraser_width": 22
    }
  }
}
```

Поведение:
- Хост при `snapshot_request` отправляет snapshot адресно (`destinationIdentities`).
- При получении snapshot клиент полностью заменяет локальное состояние доски.

## 5.4 Инструменты и операции
- Рисование (pen), ластик (eraser), фигуры (`rectangle`, `circle`, `arrow`), `text`, `sticky`.
- `clear_all` очищает доску у всех.
- Фон синхронизируется отдельным событием (`whiteboard_background_change`).
- Настройки кисти синхронизируются (`whiteboard_brush_config_change`).

## 5.5 Надежность доставки
- Критичные события (`open`, `snapshot`, `add/update/remove`, `clear_all`) отправляются reliable.
- Частые движения (`strokeMove`, часть eraser-движений) могут идти unreliable + throttle (~16ms).

## 5.6 Экспорт
- Экспорт в `PNG`.
- Дальше отправка PNG в выбранные чаты (multi-select) как image.

## 5.7 Что важно для веба
- Canvas рендер должен работать с normalized coordinates.
- Нужны два слоя состояния:
  - `persisted elements`
  - `activeRemoteStrokes` (временные, пока stroke не завершен)
- Обязательно реализовать snapshot-flow, иначе при reconnect/late-join будет рассинхрон.
- При disconnect блокировать рисование, при reconnect запрашивать snapshot.

---

## 6. Единые UX-правила для веб-версии

- Все интерактивы должны работать без перезагрузки основного медиа-потока.
- Любая панель (чат, реакции, доска) не должна блокировать кнопки звонка `mic/cam/hangup`.
- Потеря DataChannel не должна ронять весь звонок: только показать fallback-state интерактива.
- Все входящие payload парсить через type-safe слой и игнорировать невалидные поля без крэша.

---

## 7. Минимальный чек-лист перед релизом веба

1. `Raise hand`: синхронно включается/выключается у всех участников.
2. `Call chat`: работают `Всем` и `Лично`, непрочитанные считаются корректно.
3. `Reactions`: есть throttle, нет дублей, авто-исчезновение работает.
4. `Whiteboard`: join/reconnect корректно получает snapshot.
5. `Whiteboard`: clear/background/brush синхронизируются у всех.
6. `Whiteboard export`: PNG успешно отправляется в выбранные чаты.
7. На слабой сети интерактивы деградируют мягко, звонок не падает.
