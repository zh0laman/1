# Mobile E2EE Post-QR Investigation

## Цель документа

Этот документ нужен mobile-команде как итог уже проведенной проверки со стороны web.

Здесь зафиксировано:

- что именно уже проверено на web
- какой симптом наблюдался после QR linked-device flow
- что подтвердили mobile и backend по своему коду
- где сейчас наиболее вероятный root cause
- что mobile нужно проверить и исправить у себя

Документ не про общую архитектуру E2EE, а именно про баг:

**после QR scan старые сообщения на web расшифровываются, а первое новое personal E2EE сообщение иногда приходит без `encrypted_keys[current_web_device_id]`.**

---

## Краткий итог

На текущий момент наиболее вероятная причина находится на mobile стороне:

- после `approve` новый `web_device_id` уже должен существовать на backend
- `history sync` корректно помогает расшифровать старые сообщения
- но mobile может отправить первое новое personal сообщение по stale локальному кешу device keys
- из-за этого в `keys[current_web_device_id]` или `encrypted_keys[current_web_device_id]` ключ для web может отсутствовать
- следующее сообщение уже может шифроваться корректно, когда кеш обновился

То есть проблема сейчас выглядит как:

**post-QR stale key cache / first-message fan-out race на mobile**

а не как web decrypt bug и не как history sync bug.

---

## Что уже проверено на web

Со стороны web уже подтверждено следующее:

1. Web умеет расшифровывать старые сообщения после history sync.
2. Web умеет расшифровывать новые сообщения, если в `encrypted_keys` реально присутствует ключ для текущего `web_device_id`.
3. Формат mobile V4 уже учтен на web:
   - `content = base64(iv[12] + ciphertext + tag[16])`
   - `keys[device_id] = base64(ephemeral_pub[32] + key_iv[12] + encrypted_message_key + key_tag[16])`
4. На web уже есть точная диагностика причин недешифровки:
   - `encrypted_keys has no entry for device ...`
   - `Decrypt failed ...`
   - отсутствие private key
   - отсутствие current web device id

Критичный факт:

- когда web показывает `encrypted_keys has no entry for device ...`, это означает, что проблема не в дешифровке
- это означает, что нужного wrapped key вообще нет в payload сообщения

---

## Наблюдаемый runtime сценарий

По факту был замечен такой сценарий:

1. Пользователь сканирует QR.
2. Backend и mobile проводят linked-device flow.
3. Старые сообщения на web начинают расшифровываться.
4. Первое новое сообщение после QR иногда не открывается на web.
5. Следующее новое сообщение уже открывается нормально.

Это очень важная последовательность.

Если:

- старые сообщения уже расшифровываются
- а первое новое сообщение после QR не открывается
- но следующее уже открывается

то это почти идеально совпадает с гипотезой:

**новый web-device уже зарегистрирован, но mobile первое время использует stale cache списка устройств для fan-out новых сообщений.**

---

## Что подтвердила mobile-команда по своему коду

По вашему ответу mobile уже подтвердили следующее.

### 1. Явной инвалидации key cache после approve/history sync/redeem сейчас нет

В mobile коде есть:

- `_publicKeyCache`
- `_lastKeyFetchTime`
- `_minFetchInterval = 10 seconds`
- основной путь отправки новых personal E2EE сообщений использует `_getCachedUserKeys(...)`
- после `approve` и после `history sync` кеш не сбрасывается принудительно

Это уже само по себе сильный индикатор root cause.

### 2. Гарантии, что новый `web_device_id` попадет в fan-out первого нового сообщения, сейчас нет

Mobile подтвердили:

- логика fan-out концептуально правильная
- используется `recipientDevices + senderDevices + currentMobileDevice`
- `senderDevices` и `recipientDevices` приходят через `_getCachedUserKeys(...)`
- если кеш stale, новый `web_device_id` может не попасть в `keys`

### 3. Первый post-QR message действительно не гарантирован кодом

Mobile прямо подтвердили:

- runtime-тест обязателен
- текущая кодовая логика не гарантирует наличие `keys[current_web_device_id]` в первом новом сообщении после QR

Это уже очень близко к признанному root cause.

---

## Что уточнил backend

Backend отдельно указал важное различие между двумя механизмами.

### 1. Регистрация нового web-device происходит на `approve`

По backend-коду:

- новый `web_device_id` должен попадать в key registry уже во время `POST /api/v1/e2ee/web/pairing/sessions/{id}/approve`
- это не должно зависеть от `history sync`

Следовательно:

**если mobile сразу после approve отправляет новое сообщение без ключа для web-device, это уже не объясняется тем, что history sync еще не завершился.**

### 2. `history sync` нужен для старых сообщений, а не для появления устройства в `/e2ee/keys`

Backend отдельно отметил:

- `history sync` дописывает `encrypted_keys[web_device_id]` в старые сообщения
- но не регистрирует устройство в key registry

Следовательно:

- история и новый fan-out это две разные проверки
- нельзя смешивать их в одну причину

### 3. Наиболее вероятен client-side race на mobile

Backend прямо указал:

- `/api/v1/e2ee/keys/{user_id}` читает данные из репозитория напрямую
- `approve` пишет новый `device_id` в БД до возврата ответа
- значит сценарий "первое новое сообщение после QR не содержит ключ для web device" гораздо больше похож на stale local cache на mobile

Это совпадает с тем, что mobile уже подтвердили по своему `_publicKeyCache`.

---

## Почему web не является главным подозреваемым

Это важно явно зафиксировать.

Web уже показал, что:

- умеет открыть старые сообщения после history sync
- умеет открыть новые сообщения, если `encrypted_keys[current_web_device_id]` реально есть
- начинает читать следующие новые сообщения без изменений формата, как только ключ для текущего web-device попадает в payload

То есть:

- если бы проблема была в формате `content`
- или в формате wrapped key
- или в самом decrypt на web

тогда сообщение не начало бы внезапно работать просто через несколько секунд без изменения web-кода.

Факт, что одно новое сообщение не читается, а следующее уже читается, намного сильнее указывает именно на fan-out и кеш ключей.

---

## Наиболее вероятный root cause

На текущий момент наиболее вероятная причина выглядит так:

1. Пользователь сканирует QR.
2. Mobile делает approve linked-device flow.
3. Backend уже зарегистрировал новый `web_device_id`.
4. `history sync` дошивает старые сообщения и поэтому история начинает читаться на web.
5. Но mobile отправляет первое новое personal сообщение, все еще используя stale `_publicKeyCache`.
6. В результате `keys[current_web_device_id]` отсутствует.
7. Через короткое время кеш обновляется.
8. Следующее новое сообщение уже включает `keys[current_web_device_id]` и web его расшифровывает.

Это полностью согласуется с наблюдаемым поведением.

---

## Что mobile нужно проверить у себя

### Проверка 1. Делается ли forced refresh keys сразу после approve

Нужно проверить:

- есть ли сразу после успешного `approve` принудительный refresh `GET /api/v1/e2ee/keys/{my_user_id}`
- или mobile продолжает использовать `_publicKeyCache`

Ожидаемое правильное поведение:

- после approve кеш нужно инвалидировать
- первый новый personal send после approve должен брать свежий список sender devices

### Проверка 2. Инвалидируется ли `_publicKeyCache` после linked-device flow

Нужно проверить:

- сбрасывается ли `_publicKeyCache`
- сбрасывается ли `_lastKeyFetchTime`
- не мешает ли `_minFetchInterval = 10 seconds` получить свежие ключи сразу после approve

Ожидаемое правильное поведение:

- approve должен ломать обычный TTL-кеш для `my_user_id`
- первый send после approve не должен ждать истечения 10 секунд

### Проверка 3. Что реально уходит в первом post-QR message

Нужно снять у mobile:

1. `current_web_device_id` из QR flow
2. свежий ответ `GET /api/v1/e2ee/keys/{my_user_id}` сразу после approve
3. `keys` первого нового personal сообщения после QR
4. `keys` второго нового personal сообщения после QR

Нужно проверить:

- есть ли `current_web_device_id` в `GET /e2ee/keys/{my_user_id}`
- есть ли этот же `current_web_device_id` в `keys` первого нового сообщения
- если нет в первом, но есть во втором, это и есть подтверждение stale cache race

### Проверка 4. Не идет ли первый send без рефреша собственного sender device list

Нужно отдельно проверить порядок вызовов:

1. approve
2. history sync
3. first personal send

И ответить:

- mobile перед первым send реально повторно читает sender keys
- или использует уже загруженный ранее кешированный список устройств

---

## Что mobile желательно исправить

### Минимально необходимое исправление

После успешного linked-device approve mobile должен:

1. инвалидировать локальный key cache
2. форсированно перечитать `GET /api/v1/e2ee/keys/{my_user_id}`
3. только после этого отправлять первое новое personal E2EE сообщение

### Практически это означает

Нужно обеспечить, чтобы после approve:

- `_publicKeyCache` для `my_user_id` больше не считался валидным
- `_lastKeyFetchTime` не блокировал немедленный refresh
- `_getCachedUserKeys(...)` для первого post-QR send либо шел с `forceRefresh`, либо bypass-ил кеш

### Важный инвариант

После `approve` и до первого нового personal send mobile должен гарантировать:

**новый `web_device_id` уже присутствует в sender devices, используемых для fan-out.**

Без этой гарантии первый post-QR message останется случайным.

---

## Что считать успешным результатом после фикса

Фикс можно считать корректным, если воспроизводится такой сценарий:

1. Сканируем QR.
2. Делаем approve.
3. Делаем history sync.
4. На web старые сообщения читаются.
5. Самое первое новое personal сообщение после approve тоже читается на web.
6. В payload этого сообщения есть `encrypted_keys[current_web_device_id]`.

Если это выполняется стабильно, значит проблема устранена.

---

## Что сейчас НЕ выглядит основной причиной

На текущем этапе это уже не похоже на:

- общий web decrypt bug
- проблему websocket
- проблему UI
- проблему только в `history sync`
- ошибку формата `content`, если последующие новые сообщения уже читаются

---

## Финальный вывод

По совокупности наблюдений, ответов mobile и замечаний backend наиболее вероятная проблема находится в mobile post-QR send flow:

- backend регистрирует новый `web_device_id` уже на approve
- history sync корректно помогает только со старой историей
- mobile не инвалидирует key cache после approve
- из-за этого первое новое personal сообщение после QR может отправляться по stale списку устройств
- поэтому `encrypted_keys[current_web_device_id]` иногда отсутствует
- через короткое время кеш обновляется, и следующие сообщения уже начинают работать

Итог:

**mobile нужно проверять и исправлять именно refresh/invalidate sender device keys после approve, а не сам web decrypt.**
